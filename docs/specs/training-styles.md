# Liftspark: training styles and a new first run

Status: draft for 1.1 or later. 1.0 (strength only) is in App Review and is not changed by this document.
Author: spec for Akshay Kalapgar. Everything here stays on device, rules based, deterministic, with no accounts, analytics or LLM (the Coach stays off).

Scope decision (Akshay, 2026-10-25): the near term phases cover only the styles that current legal content can serve: gym strength, calisthenics and bodyweight, HIIT, running and cardio, home with little or no equipment, and mixes of those. Dance cardio, Pilates and yoga are a separated later phase that needs content sourcing first; the onboarding does not offer them before that content exists.

## 1. Goals and non-goals

### Goals

1. A new user says how they train (one or more of the supported styles), and the app's first plan, Home screen, Start button, logging screen, Health export and calorie math match it.
2. Existing lifters lose nothing: the strength path stays the default and the data model is additive.
3. The first run takes under 60 seconds and ends on a generated plan with "Start" one tap away.
4. Every claim in the App Store listing, and every choice in onboarding, is backed by content that is in the binary.

### Non-goals

- No server, account, analytics, LLM or remote content. Everything is in the bundle or typed by the user.
- No revenue, ads, IAP or paid tiers (F-1 STEM OPT). Spending on content is fine; earning is not.
- No dance cardio, Pilates or yoga in 1.1 or 1.2: not in onboarding, not in templates, not in the listing (see section 11, phase 1.3).
- No GPS run tracking in 1.x (see 5.4). Distance comes from the user or from Apple Watch via Health.
- No reuse, extraction, derivation or AI prompting of openGym's Gym visual media (NOTICE.md lines 78 to 95). Liftspark ships none of it and never will.

### 2.5 Strain and calories

`src/lib/strain.js`: five zones (Karvonen when `restHr` is known), Edwards TRIMP, `strainOf(trimp) = 21 x (1 - e^(-TRIMP/160))`, `keytelKcal` from average HR, `metKcal({ minutes, kg, met = 5 })` as fallback, Health active energy wins when present (`workoutMetrics`, lines 88 to 112). Without heart rate the strain estimate is a flat `strainOf(minutes x 2 x 0.8)` (zone 2 at 80% of the minutes) whatever the activity. The MET default of 5 is strength training. None of this knows the style; all of it works for any style once a style MET and a style zone assumption are passed in.

### 3.3 Style METs and no heart rate strain

Used by `workoutMetrics` when there is no heart rate and no Health energy. Values from the 2011 Compendium of Physical Activities, rounded; they are estimates and the UI already says so ("Estimates, not medical advice").

| Style or template | MET | Zone assumed without HR | Note |
|---|---:|---|---|
| strength (existing default) | 5.0 | Z2 | keep `met = 5` |
| calisthenics, moderate | 5.0 | Z2 | vigorous templates 8.0 |
| hiit | 8.0 | Z4 for work minutes, Z1 for rest minutes | the timer knows the split, so pass work and rest minutes separately |
| run, easy | 8.3 | Z2 | by pace when known: 5 mph 8.3, 6 mph 9.8, 7 mph 11.0 |
| walk | 3.5 | Z1 | |
| cardio machine, steady | 7.0 | Z2 | cycling 6.8, elliptical 5.0, rowing 7.0, stairs 9.0 |
| deferred: dance cardio | 7.3 | Z3 | "aerobic dance, general" |
| deferred: pilates | 3.0 | Z1 | |
| deferred: yoga, mobility | 2.5 | Z1 | |

Rule change in `strain.js`: `workoutMetrics(w, { ..., style })` replaces the flat `strainOf(minutes x 2 x 0.8)` with `strainOf(sum over blocks of minutes x zoneIndex x 0.8)` where `zoneIndex` is the assumed zone for that style (1 to 5). With heart rate present nothing changes: TRIMP from zones is already style agnostic, which is the point of using it for cardio styles.

## 4. Personalization model

### 4.1 Profile fields (new)

Stored in `S.lsProfile` (already synced to iCloud by `ls-icloud.js` PREF_KEYS and persisted by the normal store):

```js
lsProfile.styles = ['hiit', 'strength']   // ordered, primary first, 1 to 3 entries, ids from STYLE_IDS
lsProfile.place  = 'gym' | 'home' | 'bodyweight' | 'custom'   // moved here from lsOnboarding.a.place (kept there too for the run)
lsProfile.stylesAt = 1730000000000        // when styles were last set, for the migration card
```

`STYLE_IDS` in 1.1: `['strength', 'calisthenics', 'hiit', 'run', 'cardio']`. The deferred ids are reserved in a separate `DEFERRED_STYLE_IDS` constant so stored state can never carry a style the UI cannot show; the generator ignores unknown ids.

Routine fields (additive, `S.routines[]`):

```js
routine.kind  = 'sets' | 'interval' | 'session'   // default 'sets' when missing
routine.style = 'strength' | 'calisthenics' | 'hiit' | 'run' | 'cardio' | undefined
routine.blocks = [ { kind: 'work', sec: 40 }, { kind: 'rest', sec: 20 }, ... ]   // only for kind 'interval' (phase 1.2)
routine.targetMin = 30                              // only for kind 'session' (run without a machine, freestyle cardio)
```

Workout fields (`S.workouts[]`, written by `ls-workout.js attachMetrics`):

```js
w.ls.style  = 'run'
w.ls.hkType = 'running'       // the name health-connect.js sessionType returns
w.ls.outdoor = true | false
w.ls.distanceKm = 5.2         // optional
```

No field is required; every reader falls back to today's behaviour when a field is missing.

### 4.2 Deterministic generator

`src/lib/ls-plan.js` becomes `generatePlan(answers, variant)` over `answers = { styles, goal, level, days, minutes, place, equipment }`. One function, no randomness, same input gives same output (as today).

Steps:

1. Allocate days to styles. `days` training days split by position in `styles`: one style gets all days; two styles get ceil/floor (3 days: 2 + 1; 4 days: 2 + 2; 5 days: 3 + 2); three styles get 2 + 2 + 1 or 2 + 1 + 1. Primary style gets the larger share and the first weekday. Fixed weekday layout per day count, reusing the day sets already in `SPLITS` (1,3,5 for 3 days; 1,2,4,5 for 4 days; and so on), so the existing tests on `week` keys keep passing.
2. Pick a template set per style and day share from `STYLE_PLANS` (new file `src/lib/style-plans.js`, data only, same shape as `starter.js` `PLANS` plus `kind` and `blocks`):

| Style | Templates (`variant` steps through them) |
|---|---|
| strength | existing `SPLITS` (unchanged) |
| calisthenics | `cal-full` (push, pull, legs, core each session), `cal-upper-lower`; built from body weight ids with `buildStarterPlan`'s fitting against `['pull-up bar']` or the custom list |
| hiit | `hiit-20` (40/20 x 8, 2 blocks), `hiit-30` (30/30 x 10, 3 blocks), `emom-20`; each round names 4 to 6 moves from plyometrics and calisthenics; in 1.1 expressed as `kind: 'sets'` rows in `time` mode (sec) with the per exercise rest set to the rest interval, so the existing rest timer drives it; `kind: 'interval'` arrives with the timer in 1.2 |
| run | `run-base` (easy 30, easy 30, long 45), `run-intervals` (easy, 6 x 2 min hard with 2 min easy, long); entries are the running id in `cardio` mode with target minutes; `distanceKm` optional; a walk variant for `level = new` |
| cardio | `cardio-machine` (steady 30, intervals 25, steady 40) on the machine the equipment list has; falls back to `hiit` when no machine is available |
| home shortcut | `calisthenics` + `hiit` templates with `place = bodyweight` or `home` |

3. Fit to equipment with `buildStarterPlan`'s `fitRoutines` for `sets` routines (unchanged); `session` and `interval` routines skip fitting.
4. `tune()` as today, by goal and minutes, plus per style caps: HIIT never gets reps nudged; run minutes scale with `minutes`.
5. Return `{ label, splitId, routines, week, missing, styles }`. `applyPlan` unchanged.

Testable invariants: one routine per planned day, no `missing`, every `sets` routine passes `eqAvailable`, every routine of a non strength style carries `kind` and `style`, same answers twice gives deep equal output, `variant` wraps, unknown or deferred style ids are dropped before allocation.

### 4.4 Mixing styles across a week

- The generator interleaves (4.2 step 1). The Plan tab's weekday grid already shows one routine per day; a routine's `style` glyph makes the mix visible without new UI.
- Day override sheet (`dayOverrideSheet`) lists routines grouped by style.
- Rotation mode (`S.scheduleMode === 'rotation'`) works unchanged: routines of any kind can be added to the loop.

### 4.5 Changing style later

- Settings > "Training style" (new row next to "Redo onboarding", `Settings.jsx` line 978): opens the style screen alone, then offers "Rebuild my week" (runs `generatePlan` with the saved answers and the new styles, shows the plan screen with "Replace plan" or "Keep my routines and add these") or "Keep my plan". Routines are never deleted by a style change; `applyPlan` only appends and reassigns weekdays, as today.
- "Redo onboarding" keeps working and starts at the style screen with the saved answers prefilled.
- Day level: the day override sheet lets a user put a HIIT session on a strength day without touching `styles`.

### 5.4 GPS or not

Recommendation: no GPS in 1.x.
